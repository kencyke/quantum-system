# Lean Lint Rules

The rules that hold in any Lean 4 project following Mathlib style. A project states its own rules in
a rules file that its instruction file (`CLAUDE.md` / `AGENTS.md`) names — prohibited tokens, pinned
files, commit style, a different line limit — and those add to these and win where the two differ.
`lake build` and `lake lint` detect part of the rules; the `lint-fix` skill lists which.

Each rule carries the reason it exists where the reason is not self-evident. The
reasons are load-bearing: they are what lets you judge an edge case the bullet
does not literally cover, instead of guessing.

## Editing Hygiene

- Spaces only, never tabs, in Lean sources.
  **Why:** the Lean lexer rejects tabs. Whether other files follow suit is for the project rules to say:
  in some (a Makefile recipe, a TSV) a tab is syntax.

## Unfinished Proofs

- `sorry`, `admit` and `axiom` mark a proof that is not there. They are reported, never "fixed".
  **Why:** deleting the token leaves an unproved goal or removes a declaration others depend on; the only real fix is
  a proof.

## Style Guidelines

The Mathlib contribute templates are authoritative; the bullets below distill what actually comes up during edits.

**Naming.**
- `lowerCamelCase` for terms and definitions (`orderOf`, `toFun`).
- `UpperCamelCase` for types, structures, and propositions (`TopologicalSpace`, `IsCompact`).
- Theorem names use `_` as word separator (`norm_add_le`, `inner_self_nonneg`).
- Prefer the `_of_` pattern for implications (`continuous_of_lipschitz`); `iff` joins equivalences; `not_` prefixes negations.

**Layout.**
- 100-column line limit (Mathlib's `linter.style.longLine`), unless the project sets another.
- 2-space indentation; `by` stays on the same line as the goal it opens unless the resulting line would exceed the limit.
- Hoist shared hypotheses into `variable` blocks; keep explicit/implicit arity consistent with sibling lemmas.
- Align `calc` steps on the relation; use `·` (centered dot) for focused goals, not `case _ =>`.

**Docstrings.**
- Every definition, structure and class gets a `/-- ... -/` docstring whose first sentence is a self-contained
  summary; so does every main theorem.
- Declarations generated by `@[simps]` and `@[ext]` (e.g. `*_apply`, `ext_iff`) are exempt.
  **Why:** they have no source text to carry a docstring.
- Module docs (`/-! # Title ... -/`) at the top of each file describe the content and any non-obvious conventions.
