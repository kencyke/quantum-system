# Project Lint Rules

The authoritative statement of this repository's own editing hygiene, prohibited tokens, commit style,
and style guidelines — the one place to edit when a rule changes. `AGENTS.md` points here, and the
`lint-fix` skill fixes violations. These rules add to the generic Lean rules that ship with the skill
(`plugins/lean-formalization/skills/lint-fix/references/rules.md`) and override them where the two differ. `lake build`
and `lake lint` (both run in CI) detect part of the rules; the `lint-fix` skill lists which.

Each rule carries the reason it exists where the reason is not self-evident. The
reasons are load-bearing: they are what lets you judge an edge case the bullet
does not literally cover, instead of guessing.

## Editing Hygiene

- Spaces only, never tabs, in every file of the repository, not only in Lean sources.
  **Why:** Mathlib style, and indentation in other files should match.
- As an agent, never modify `lakefile.toml`, `lean-toolchain`, or `lake-manifest.json`. Changes to them come
  from the user or from the Mathlib bump workflow (`update_mathlib.yml`), and are not violations.
  **Why:** the toolchain and manifest are pinned intentionally; accidental edits cascade into reproducibility failures.
- Regenerate the aggregate `QuantumSystem.lean` with Mathlib's script, `lake exe mk_all --lib QuantumSystem`.
- Write comments in English.
- Never create namespaces or sections named `QuantumSystem`.
  **Why:** declarations are named as their Mathlib counterparts would be (`DirectLimit.…`, `LinearPMap.…`), so that
  `ForMathlib/` can be upstreamed; the module path `QuantumSystem.…` names files, not declarations.

## Prohibited Tokens

The following tokens are strictly prohibited in Lean sources, grouped by reason.

- *Unsound or deferred proofs:* `sorry`, `admit`, `axiom`.
  **Why:** the project targets a fully axiom-free formalization; assumptions smuggled into structure fields count as axioms too.
- *Global configuration and unsafe code:* `set_option`, `unsafe`.
  **Why:** these mutate kernel or elaborator behavior project-wide, or bypass soundness.
  **Exception (approved 2026-10-03):** `set_option maxSynthPendingDepth 2 in`, scoped to single
  declarations of `QuantumSystem/InformationTheory/Entropy/VonNeumann/StrongSubadditivity.lean`. Operators on
  a three-fold tensor product `(A ⊗ B) ⊗ C` need a depth-2 nested instance search while unifying
  the inner factor's algebraic and normed instances, which Mathlib's default depth `1` refuses; the
  option only raises a type-class search limit and does not affect soundness. See the section
  *Nested tensor products* of `ForMathlib/Analysis/InnerProductSpace/TensorProduct.lean`. Any other
  use still needs explicit approval.
- *Compiler and metaprogramming internals:* `System`, `open System`, `Lean.Elab`, `Lean.Meta`, `Lean.Compiler`.
  **Why:** this is a mathematics repository, not a tactic-library repository; depending on internals creates brittle code.
  The same holds for `macro`, `meta def`, delaborators (`delab`) and unexpanders (`app_unexpander`): a notation is
  displayed by shaping the definitions it unfolds to, so that the unexpander generated by an ordinary `notation`
  declaration fires — a proof-free `def` in place of a term carrying a proof argument (`sqrtModular K` rather than
  `IsSelfAdjoint.sqrt (isSelfAdjoint_modular K)`), a `Prop`-valued class in place of hypotheses passed explicitly or
  found by a tactic (`[IsCyclicSeparating M Ω]`), an implicit argument in place of a `_` placeholder in the notation.
  When two notations unfold to the same constant (`Δ[K]^{i t}` and `Δ[K]^{-i t}`), the one declared later is tried
  first when displaying.
  **Exception (approved 2026-10-10):** the delaborator `delabAdjoint` in
  `QuantumSystem/ForMathlib/Analysis/InnerProductSpace/Adjoint.lean`, which displays Mathlib's `A†`. Mathlib's `†`
  for `ContinuousLinearMap.adjoint` is never displayed, because the adjoint is a bundled equivalence and `A†`
  elaborates to its coercion applied to `A`; no definition in this repository can change that without bridging two
  spellings of the adjoint. Any other `macro`, `meta def`, delaborator or unexpander still needs explicit approval.

## Commit Style

`lefthook` + `commitizen` (`cz check`, configured in `pyproject.toml`) enforce this; the accepted
vocabulary is:

- Conventional Commits: `feat` / `fix` / `chore` / `docs` / `refactor` / `test` / `perf`.
- Lowercase type, colon, imperative subject. Example: `feat: add GNS faithfulness lemma`.
- One logical change per commit.

The hook runs the stock `cz_conventional_commits` schema, which also accepts `build` / `ci` /
`style` / `revert` / `bump`; the list above is the deliberately narrower project convention.

## Style Overrides

**`theorem` versus `lemma`.**
- Reserve `theorem` for the headline results a file exists to prove — the statements a textbook
  would call a theorem (a spectral theorem, a uniqueness or existence theorem, Tomita's theorem,
  Borchers' Theorem A). Everything else — API lemmas, rewriting rules, intermediate steps, the
  `_iff`/`_of_` bookkeeping around a definition — is a `lemma`, and anything used only inside the
  file is a `private lemma`.
- A rule of thumb: if the declaration is listed under "Main results" in the module doc with a bold
  name, it may be a `theorem`; a file rarely needs more than a handful.
  **Why:** `theorem` marks what a reader should look at first. When most declarations carry it,
  the marker stops carrying information and the main results disappear in the noise.

**Layout.**
- 120-column line limit, in place of Mathlib's 100 (`linter.style.longLine` is off in `lakefile.toml`).
  The limit applies to Lean code; the repository's markdown may exceed it.

**Docstrings.**
- Every public declaration, theorems and lemmas included, gets a `/-- ... -/` docstring whose first sentence is a
  self-contained summary. The generic rules' exemption for declarations generated by `@[simps]` and `@[ext]` still
  applies.
